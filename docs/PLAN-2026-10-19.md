## The rule for tomorrow (the user, 2026-10-18 21:2x)
"We don't want to make bandaid fixes for all of these things. We want a clean implementation of TF.EX that works as intended, just
adjusted to work on the switch." And: the stretched remote archer is "a sign that something underneath the hood is wrong".

So every fault below is a **symptom**. Before anyone fixes one:
1. Trace it to the piece of code it runs through, and say whether that piece is TF.EX's own code (generated), a real Switch
   difference (a TFEX-DIFF with its reason), or **our own imitation of TF.EX** (a hand port, a [service] rule standing in for TF.EX,
   the Switch's whole-heap rollback where TF.EX restores TF.State's entities).
2. If it's our imitation, the fix is to replace that piece with TF.EX's code (or make the TFEX-DIFF match what TF.EX's code expects),
   not a patch at the symptom. A patch at the symptom (a null check, a clamp, a resync, a special case) needs the user's OK.
3. If it's TF.EX's own code, it's a translator or binding fault (today: try/finally, the TryParse binding): fix the translator.
The remaining imitations, the likely sources of most symptoms: the TF.State gameplay patches (hand ports in rnd.cpp / xplay.cpp,
item 2), the input/controller services, and the rollback's state model (the whole GC heap restored, with the NetplayManager's state
carried across by hand, where TF.EX restores only TF.State's entities).

### 1b. The crash on returning to the menu (raised from item 5: it now crashes after every lobby match)
TF.EX's InputService.EnsureLocalControllerSeat (svc::EnsureLocalControllerSeat, tfex/runtime/tfexgen_services.cpp:100-118) moves the
local controller to the player's seat and leaves a null in its old `TFGame.PlayerInputs` slot, as TF.EX does on PC. The Switch's
MInput.UpdateJoysticks calls UpdateStyle on `PlayerInputs[i]` for every attached JoyCon, so a null slot crashes on the next menu
frame. Fix (a TFEX-DIFF, docs/ws-tfex-update.md "Menu crash 01792332348", option a): the vacated slot gets a real input object for
that attached controller, not a null check. Likely the same code path as the "second controller pair takes a slot" fault (item 5).
**Owner:** translator. Small; do it first tomorrow beside item 1.

### 3. Stretched remote archer: a sign of a deeper fault, not a rendering bug to patch
The remote (browser) archer drawn stretched across the whole screen width, seen several times today. Treat it as evidence that the
remote player's state on the Switch is wrong underneath (the user). An archer's sprite spans the screen when its position and its
previous / render position are a screen width apart (TowerFall draws wrap copies at the edges), or when its scale/frame data is
garbage: either way **the remote Player object holds state the browser's doesn't**. Candidates, in the rule's terms:
- the rollback's state model (our whole-heap restore + hand-carried state vs TF.EX's TF.State entity restore): a field restored
  from a different frame than its neighbours, or memory the restore freed and the game reused (today's VList / container bugs
  were exactly this class);
- the hand-ported TF.State patches (item 2) setting player state TF.EX's patches set differently;
- the remote input path (TF.EX's InputService vs our input services).
**First:** when it happens, log the remote Player's position, previous position, scale and the frame (bounded), and compare with
the browser's digest of the same frame. It will very likely line up with item 1's desync: fix the cause there, not the drawing.
**Owner:** with item 1 (B2), since both are "the Switch's simulation of the remote player differs".
