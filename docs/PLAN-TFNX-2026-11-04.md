# TF.NX: sharing the Switch mods (plan, 2026-11-04)

Background and research: docs/DISTRIBUTION-2026-11-04.md (the conversation's decisions, the plugin-loader proof). Related plans this one
leans on: docs/PLAN-MOD-MODES-ONLINE-2026-10-31.md (mod game modes online: MoveOrDie, Respawn, TowerBall), docs/PLAN-8-PLAYERS-2026-11-02.md
(8 players online), docs/PLAN-THREETEAM-FORTRISE-2026-10-31.md (Teams+), docs/ws-wide.md (wide levels).

## 1. What a player does (the target)

The player has a hacked Switch with TowerFall 1.4.1.6, and nothing else: no PC, no game dump, no PC copy of TowerFall.

1. Downloads one zip (the TF.NX release) and extracts it to the SD card root.
2. Optionally drops PC mod folders into `sd:/xplay/mods/` (archer mods from GameBanana, WiderSet's own download, ...).
3. Starts the game. Mods on the MODS screen; each one loaded or not, and why not.
4. Plays locally and online (TF.EX lobbies, crossplay with the PC and the browser).

Later, optional: a homebrew app that does steps 1-2 over Wi-Fi (download, update, remove). Never needed for the game to work.

## 2. The shape

**TF.NX** (one `subsdk9`, the core): TF.EX (translated), the Switch port of FortRise (its content loader, mod registry, MODS screen, mode
registry), the Switch's own systems (rollback, transport, wide mode), and the **logic of every built-in mod**: each one dormant until
its folder is present.

**A mod folder** (`sd:/xplay/mods/<Mod>/`) is the PC release as it is: `meta.json` (name, version, dependencies) and `Content/` (art,
levels, sounds). The PC's DLL is ignored on the Switch: its translated logic is in TF.NX.

**Three kinds of mod:**

| kind | logic | folder brings | examples |
|---|---|---|---|
| content | none (FortRise's content loader) | everything | archer mods, skins, towers |
| built-in | in TF.NX, translated from the PC mod at a known version | art, levels, sounds, meta.json | Teams+, Soccer, Respawn, MoveOrDie, TowerBall (FortRise version), WiderSet |
| unknown code mod | none on the Switch | its content still loads | any PC code mod we haven't translated |

An unknown code mod shows on the MODS screen as "code mod: not on the Switch" and its content loads only if it is content-safe without
its code (default: not loaded; it would desync or crash).

**Not chosen (and why):** separate code plugins (docs/DISTRIBUTION "Code plugins": proven in Ryujinx, parked: a plugin is tied to one
core version anyway, so it buys little until outside modders build Switch plugins); prebuilt combinations (2^n builds); a .NET
interpreter (years).

## 3. Compatibility: folder vs built-in logic

TF.NX records, per built-in mod, at translate time: the version its logic is translated from, and the **files its logic reads from the
mod's folder** (a manifest). At boot (the mod registry, tfexgen_mods.cpp `Resolve`):

- the folder has every manifest file -> the mod loads, whatever its version;
- a manifest file is missing -> the mod doesn't load; the log and the MODS screen name the file;
- the folder's version differs from the logic's -> loads, one notice line (`[mods] Teams+: folder 0.1.2, TF.NX runs 0.1.1's logic`);
- online, TF.EX's lobby mod list carries the **logic's** version (what plays), so a PC player on another version sees TF.EX's usual
  mismatch warning.

How the manifest is made: the translator lists the mod's own asset paths it sees in the code (FortRise's `@`-prefixed names and the
mod's `Content` paths) plus a hand list in translate.toml for what it can't see; a file the list misses shows as a load error the first
time the game asks for it (logged, not a crash: the loader's existing missing-texture path). Checked once per mod with a folder that
lacks one file.

### Adding a mod to TF.NX

**Restructured 2026-11-04: one folder per mod, mods/<name>/ (mod.toml, meta.json, src/, its folder builder); the recipe and the rules
(FortRise's mechanisms first, mods publish APIs instead of reaching into each other, two boot phases, per-mod hook counts,
tools/mods/check.sh) are mods/README.md. The list below is the first version, kept for the record.**

1. **Its logic in the module:** a translated FortRise mod (translate.toml `[[unit]]`s over its vendored source, as Teams+) or our own
   native code (as TowerBall, megamod/towerball*.hpp). Its hooks go in from its **boot** function, never at boot time, so the mod is
   dormant without its folder.
2. **A catalog entry,** `[mods.catalog."<meta.json name>"]` in translate.toml: `meta` (its meta.json in the repo: the version its
   logic is), `src` / `needs` (the files its folder must have), `boot` (the C++ function), and if it needs them:
   - `replaces`: game textures its own replace while it's loaded (`{ id, with, atlas }`; TowerBall's ball and mode banner);
   - `overlay`: game files its folder supplies while it's loaded (`*` = one path segment; served when the game loads one through
     Calc.LoadXML, XML files: levels, tower data; TowerBall's `tb.oel`);
   - the overview keys (`source`, `download`, `permission`, `works`).
   Regenerate gen/ (translate.sh all) and docs/MODS-CATALOG.md (tools/mods/catalog.py).
3. **Its folder:** the PC release as it is, or, when its files are third-party and we build it, a line in tools/mods/folders.list
   (the emulator's SD card and the console channel get it from there; `XPLAY_MODFOLDERS=0` runs without the built folders).
4. **Its art** comes through FortRise's content loader (the folder's `Content/Atlas/*.xml`), named `<mod>/<name>` in the game's atlases.
5. **Checks:** one run of the mod with its folder (its log lines), one boot without it (dormant), and one smoke run when it touches a
   path online play uses.

## 4. What can't be shipped, and how the player gets it anyway

| thing | today | TF.NX |
|---|---|---|
| PC versus levels (40 of 141 differ from the Switch's) | copied from a PC install (tools/pc-levels.sh) | a **level delta** in the release (entity-level changes per level, ours to write), applied in memory on the console to the Switch's own levels when a level loads online |
| the megamod's art (TowerBall baskets/ball, controller icons 7/8, banner) | composited into the game's atlases (tools/megamod/romfs.py) | **our art only**, in a folder, registered at runtime through FortRise's sprite / subtexture registries; no game atlas rewritten |
| WiderSet's levels (`PCWide`) | copied from a WiderSet download | WiderSet's own folder: the player downloads WiderSet from GameBanana and drops it in (its levels are read from there) |
| the 8-player spawn-edited `6P-Versus` levels | 209 edited game levels in the romfs | retired: local 8 players plays WiderSet's levels too (same as online) |
| third-party mods' art | - | always the mod's own folder (the player's download) |

So the release contains only our code and our files. The romfs layer goes away (step 2 ends with an empty romfs).

## 5. Permissions (needed before a mod's logic ships in a release)

Our own: TF.NX glue, Teams+ (TeamsPlus), our art. Licences checked 2026-11-04:
- **TF.EX: GPL-3.0** (vendor/tfex/LICENSE). TF.NX's module contains translated TF.EX, a derivative work: shipping it is allowed if
  TF.NX as a whole is released under GPL-3.0 with its full source (this repository, translator and gen/ included). Ask Fcornaire
  anyway (courtesy, and the name "TF.NX").
- **FortRise: MIT** (vendor/fortrise/LICENSE): fine inside a GPL-3.0 TF.NX; keep its copyright notice.
- **exlaunch: GPL-2.0** (hw-probe/exlaunch/LICENSE; no "or any later version" found in the tree): GPL-2.0-only and GPL-3.0 code can't
  be combined in one binary. Upstream checked 2026-11-04 (shadowninja108/exlaunch): GitHub says GPL-2.0, the LICENSE is the plain v2
  text, no "or later" statement in the README, no per-file headers or SPDX tags; the README credits Atmosphère (GPL-2.0) as a reference,
  and some lib/nx pieces look like libnx (ISC). Safe reading: GPL-2.0-only, so it blocks a GPL-3.0 release. Options: ask its author for
  "GPL-2.0-or-later" (cheapest; covers only what is theirs), or replace the parts TF.NX uses (hooks / trampolines, patching, init, the
  code-memory alias, svc wrappers; libnx-derived ISC parts can stay). Its bundled rtld is ISC (fine).
  **For now (the user, 2026-11-05): exlaunch taken as "any version".** It ships only the GPL-2.0 text, with no version notice in its
  files; GPL-2.0 section 9: a program that doesn't specify a version may be used under any version, so GPL-3.0 with TF.EX. An
  interpretation, not a settled fact (a lawyer's view would settle it); the NOTICE says so. The alternatives stay open if it's
  challenged: ask exlaunch's author, Skyline (MIT) behind exlaunch's API, or our own layer on the MIT / ISC parts (sized below).
  **Earlier decision (the user, 2026-11-04): don't count on a relicence; find an alternative.** What hw-probe/exlaunch/source/lib is made of
  (9.2k lines): the hook core is And64InlineHook (MIT, Rprop: hook/nx64/hook_impl.cpp's header), lib/nx is libnx (ISC), rtld ISC;
  diag/ and util/typed_storage.hpp come from Atmosphère (GPL-2.0); the rest (hook wrappers, patchers, init, util, armv8 encoders,
  reloc, build scripts, linker script) is exlaunch's own. Our code uses it through ~1000 call sites in 40 files (649 InstallAtOffset,
  352 HOOK_DEFINE_TRAMPOLINE, 16 CodePatcher, GetMainModuleInfo). Alternatives: Skyline (skyline-dev/skyline, MIT, maintained; a
  subsdk loader that also loads NRO plugins), or our own layer on the MIT / ISC pieces with exlaunch's API kept (the call sites
  unchanged), written fresh, not copied.
- Rust: ggrs and the other crates in ggrs-switch (MIT / Apache-2.0: fine; list them in the release's notices).
- The game itself: TF.NX hooks a proprietary game, as TF.EX does on the PC; nothing of the game ships.
- **WiderSet** (Teuria): the translated logic; its levels stay in the player's own download.
- **Soccer, Respawn, MoveOrDie** (ebe1.kenobi; we already carry forks with TF.EX's game-mode API).
- **TowerBall** (Suyooo's v3 / CoolModder's FortRise port: not redistributable, no licence): later, when we come back to it.
A mod without permission stays out of the public release (it can stay in our own builds).

## 5b. The catalog, updates, and keeping up with TF.EX (the user, 2026-11-04)

- **One catalog** of every mod TF.NX offers: `[mods.catalog]` in tools/tfex/translate.toml (the translator already owns the built-in
  mod list; the catalog is the same list's source). Per mod: its name (meta.json), the version its logic is translated from, its
  source (repo / commit), the files its logic needs from the folder, where players download the folder, its permission status, and
  what works (local, online). `tools/mods/catalog.py` prints it as a table (docs/MODS-CATALOG.md, generated, for players and for us).
- **Updates:** a TF.NX release follows (a) every TF.EX release, (b) an update of a catalog mod, (c) our own fixes. A release's notes list
  the catalog's versions. Checking for upstream updates (TF.EX tags, each catalog mod's repo or GameBanana page): a script that compares
  each catalog entry with its upstream's latest, run before each release.
- **The update check (2026-11-05): tools/updates/check.py.** One table: what TF.NX carries (TF.EX and FortRise from the generated code,
  each catalog mod's meta.json) against its upstream (GitHub releases for TF.EX and FortRise; per mod its mod.toml [update] or its
  meta.json's own update field: GitHub, GameBanana, or our own repository's meta.json; a GameBanana page without a version by date).
  Exit 2 when something is newer; tools/release.sh warns. Run twice a day: .github/workflows/update-check.yml (07:00 and 17:00 UTC; one
  open issue labelled update-check while something is newer, closed when everything is current again; inactive until the repository is
  on GitHub), meanwhile the Mac's scheduled task "tfnx-update-check" (09:00 and 19:00, read-only; delete it once the workflow runs). A
  local update source missing on the machine is reported as skipped (Teams+ has its public GitHub releases since 2026-11-06: mod.toml github).
- **TF.EX first:** the official server only lets TF.EX's latest version play online, so a TF.EX release blocks every Switch player
  online until TF.NX follows. tools/tfex/update.sh is the path (the diff between tags, retranslate, one smoke run); the target is a
  TF.NX release within days of a TF.EX one. The update check above reports a new TF.EX tag first.

## 7. Risks

- **The console:** permissions for mod logic (section 5) can block the public release; ask early, in parallel with the work.
- **Versions online:** TF.EX's server only lets the latest TF.EX version play: a TF.NX release must follow each TF.EX release quickly
  (tools/tfex/update.sh), or Switch players are locked out until it does.
- **Hook budget:** every built-in mod's hooks share 409 trampolines (324 used 15 s after boot today); step 5's "only enabled mods"
  keeps it bounded; the pools log shows it.
- **The level delta is derived from the PC levels** (accepted by the user, 2026-11-04): small, readable data, never the files.
- **Manifest gaps:** a file the manifest misses shows as a logged load error the first time it's needed (section 3).

## 9. What the Switch mods so far teach a generic FortRise translation (2026-11-05)

The goal (the user, 2026-11-05): no custom solution per mod; a FortRise mod becomes a Switch mod by translation, and every hand rule a
mod still needs is a gap in the translator or the Switch's FortRise layer, not part of that mod. Read from Teams+ (translated), Wider
Set and TowerBall (native rewrites), the content mods, and Soccer's first look (vendor/soccer, not translated yet).

**What already works generically: content.** Once FortRise.Content's loaders and its registries were translated (the `Fr_*` units),
every archer, skin, sound and music mod loaded with no per-mod work (the SSB roster, Madeline, MexicanPuppet). That is the model:
translate FortRise itself, then a mod needs only its own code translated.

**Gaps, each seen in a mod we carry:**

| # | gap | where it showed | generic fix |
|---|---|---|---|
| 1 | A patch on a method the Switch's build **inlined** misses every inlined copy (the PC's Harmony patch reaches all callers) | FrModes.cpp by hand: TeamMode in 4 MatchSettings methods, GetModeName in VersusModeButton.Render, GetScoreIndex in 9 Session methods (Teams+'s score slots threw) | at translate time, each hook target's inlined copies from the binary (tools/re callmap / parity's inline detection), reported per mod; the fixes stay per game method (as FrModes's), reused by every mod |
| 2 | **Two mods patching one method** need a hand shell | FrModes.cpp ProperlyAssigned / CreateTeamSelect shells (Teams+ and the 8-player rules) | HookGen emits Harmony's chain: every mod's prefixes and postfixes on a target, in Harmony's priority order, one trampoline |
| 3 | Mods **boot later** than on the PC (after GameData.Load, not in Main): a patch on code that already ran never fires | Teams+'s ArcherData.Initialize postfix called by hand (FrModsBoot.cpp) | boot code mods where FortRise does, or replay the load-time targets for any mod that patches them |
| 4 | **Mod-to-mod APIs** as per-member rules | Teams+'s `Wide.*`: 5 rules over WiderSet | FortRise's GetApi / ModInterop answered by the provider (a translated mod, or the Switch's stand-in implementing the interface); the consumer translates with no rules (TF.EX's IWiderSetModApi already does) |
| 5 | **Per-mod wiring by hand**: a registry function (SwitchMods.TeamsPlusRegistry), a boot function and its patch-class list (FrModsBoot.cpp), `[code_mods]` and 16 `[[unit]]` entries | renaming Teams+ touched 31 non-doc source files outside gen/ | generated from mod.toml and the vendored source: units by namespace, patch classes from HookGen's scan, the boot = construct the module + enable its classes |
| 6 | Dev / test code needs per-mod no-op rules | `TeamsPlus.SelfTest.Load` (9 Teams+ rules in overrides.toml in all) | one rule: `Environment.GetEnvironmentVariable` is null on the Switch, so those paths fall away |
| 7 | **IL transpilers** become hand native patches | Teams+: 3 (TeamPlusNative.cpp, with RE) | stays manual; a scan counts a mod's transpilers before porting, so its cost is known up front |
| 8 | Native rewrites teach the translator nothing | Wider Set (1678 lines; MonoMod patch_ classes, the Switch's wide mode stays: memory "wide mode is native"), TowerBall (3105 lines, Warlord's mode slot as a stand-in) | translate where we can; TowerBall's needs (a custom arrow: the Arrows registry, its own mode slot) are generic gaps too |
| 9 | FortRise features only TF.EX has on the Switch | Soccer, Respawn, Move or Die and FortRise's example mod all use them: `ModuleSettings` / `GetSettings<T>` per mod (the Switch's is TF.EX's NetplaySettings), `OnInitialize` (one slot, TF.EX's), the `IHookable` / `IRegisterable` reflection loop over types | per-mod settings objects (and their OPTIONS page, saved to the SD), a list of OnInitialize callbacks in mod order, the translator reading a constant `Type[]` loop of `GetMethod(name).Invoke` as static calls |

**FortRise's registries on the Switch:** 8 of the 23 in IModRegistry (Subtextures, Sprites, SFXs, Musics, CharacterSounds, Archers,
GameModes, Variants). Not yet: Arrows, Pickups, Effects, Enemies, LevelEntities, BGElements, Backgrounds, MenuStates (FortRise's own
MODS screen only), DarkWorldBosses, Tilesets, Towers, TowerHooks, QuestEvents, Themes, Commands. A mod using one fails at translate time
today; each is translated once, for every mod.

**How to measure progress:** a per-mod report from the translator: its units, hooks, rules it needed (by key), transpilers, inlined
targets, registries it uses that the Switch lacks. A mod is "automatic" when that report has no rules and no missing registry; the
number of rules each new mod needs should fall.

## 10. Translating FortRise mods on the PC (the user, 2026-11-05)

The goal is a PC-side translation that makes FortRise mods work on the Switch automatically, not a one-to-one FortRise running on the
console. So: do at translate time whatever can be read from the mod's source (its Mod class, its Harmony registrations, which patches
target load-time code, its meta.json order), and carry on the Switch only the parts of FortRise that mods rely on while they run
(load order, a context per mod, OnInitialize for each mod, its settings), where that makes sense.

Today a translated code mod still needs hand code: a registry function (glue SwitchMods.cs), a boot function with its patch-class list
and its load-time postfix called by hand (FrModsBoot.cpp). Steps:
1. **A generated boot per code mod**, from its `[code_mods]` entry and its source: its registry by meta.json name, its Mod class
   constructed, its patch classes on (HookGen already reads its Harmony registrations), postfixes on load-time targets replayed
   (`[hooks] load_time`, gap 3), its IL edits' native patches if it has any. Teams+ and the test mod lose their hand boots.
2. **OnInitialize for every mod** (FortRise calls each mod's after all are loaded; the Switch has one slot, TF.EX's).
3. **Settings for every mod** (ModuleSettings per mod, saved on the SD card; the Switch has TF.EX's only).
