# Strategy: full TF.EX on the Switch, faster (2026-10-28)

**The goal (the user):** near-automated upkeep with every future TF.EX release, and feature parity with TF.EX, played on the real
TF.EX server later on. So each step is judged by two questions: does more of TF.EX run as generated code, and does the next update
report (tools/tfex/update.sh) have less hand work because of it? A step that adds a feature through a new hand port, or a protocol
or server behaviour only our fork has, moves away from the goal even when it works.

## Where we are, measured

TF.EX at the pin (fbeec67 = v0.27.0 + #283), methods / properties / constructors, against what the translator emits
(gen/tfexgen_members.txt):

|---|---|---|---|
| all of TF.EX | 30,774 | 46,953 | 16,179 (66% runs) |
| TF.Replay (Domain, Patchs, Core) | 0 | 6,690 | 6,690 |
| TF.InputDisplayer | 0 | 934 | 934 |
| TF.State (Domain, Extensions, Patchs, Core) | 14,427 | 16,266 | 1,839 |
| TF.EX network (Services, CustomComponent, Models, Patchs, ...) | 16,347 | 23,063 | ~6,700 |

About 1,500 of the missing lines are by design and only need a skip rule: KeyboardInput (no PC keyboard), AutoUpdater,
GameFilesIntegrity, GGRSFFI / Interop / Externals / SafeBytes (the Switch's ggrs_ffi glue), TokenService (obsolete upstream), the
Ports interfaces. **Not skipped** (the user, 2026-10-28: they may help us): TF.State's debug tools (StateDiff and StateDescriber,
which TfStateApi uses to describe a desync; EntityDumper), TFCommands, DebugLayer, and the tests (InputCodecTests, ReplayComparer,
ApiSurfaceTests): candidates for the console's desync diagnosis and for host-side checks of our codec.
What is real work then:
- **replays + input display**: ~7,600 lines, self-contained (ReplayService, InstantReplayFootage / Viewer, the replay
  browser, SpectatorInputDisplay);
- **network screens and services**: ~3,500 lines, mostly MenuItem subclasses (PlayerProfilePanel 450, LeaderboardPanel 285, the
  MainMenu patch 148, SeriesScreen) and what feeds them (MatchStats / MatchStatsReport, Changelog, InputDelayAdvisor,
  TFEXModModule's tutorial);
- **TF.State**: ~1,800 lines (ChaliceGhostPatch 105, LevelExtensions, BGElementExtensions, the Core context);
- **the Switch's hand code that is still TF.EX look-alike**: 114 lines (docs/HAND-CODE-INVENTORY.md "L rows"). Track 2 of the
  thin-shell plan is nearly done; it is no longer where the gap is.

So the remaining work is finite and mostly *TF.EX code that never runs on the Switch*, not hand code to replace.

## Why it has been slow

1. **Desyncs and faults cost a session each.** Without TF.State's own desync description on the console, each one took a
   statediff run, a dump and a read-through (v0.27.0's MatchStats, the wide padding).
2. **Work picked by hand file, not by missing TF.EX.** Tracks were "replace file X"; the translator gaps a feature needs were met
   one construct at a time, mid-feature (v0.27.0: 8 constructs, each found by a failing build or run).
3. **Prose overhead.** 368 of 1,479 commits since 10-14 are docs / status / plan; 11,900 lines of docs. Tables that a script
   could print (coverage, inventory, the update report) were kept by hand too.
4. **Decisions met late.** Replays, spectators at 60 Hz, server hosting, 240 Hz were each decided when work reached them, and
   work waited.
5. **The test harness breaks on upstream UI changes** (v0.27's RANKED button, the tutorial): fixed by hand each time.

## The strategy

### 1. One number, one generated backlog (done 2026-10-28: docs/TFEX-BACKLOG.md, tools/tfex/backlog.py)
At fbeec67: 67.5% of TF.EX's lines generated, 3.1% replaced (with a reason), 0.9% hand ports, 3.3% skipped; the steps hold
2: 543, 3: 73, 4: 165, 5: 1,092, 6: 624, 7: 171, 8 (replays): 9,021 lines. The measure above counted interface members and the
protocol models' auto-properties as missing; the backlog doesn't (the models are generated as structs). The step sizes count only
TF.EX's own lines: step 3's 73 lines are what is missing there, not the work (that is tracing the Switch's side of the flow).

`tools/tfex/coverage-by-area` (the table above, from the split and tfexgen_members.txt) runs on every commit and lists each
missing member under one of: *generated*, *skip* (with a one-line reason, in overrides.toml), or a *step* below. A first pass
(half a day) puts every one of the 16,179 lines in a column; after that the backlog is a list a script prints, not prose.
Progress = lines of TF.EX running, per step.

### 2. One thing at a time, in this order (the user, 2026-10-28: no parallel development)
Each step: one session, its TF.EX code ON and the hand stand-in deleted, its members counted as *generated* by the update report
(no new hand ports; a Switch difference is a rule with its one-line reason), the translator constructs it needs added on the way
(ranked by `translate.sh coverage` at the pin; the last report is v0.21.0's, so re-run it first). Merged onto master once the
step's scenario shows it works.

### 3. Testing
- Per step: build plus the one scenario of the flow it switches (as now). Fast checks that need no emulator: translator unit
  cases for each new construct, check-gen, the inventory's D / L rows.
- The harness reads the menu by its labels where it can (the RANKED shift), so an upstream button doesn't break every script.

### 4. Less prose
STATUS.md: one short "now" paragraph and the console bug list. Coverage, inventory and update reports are generated.
Commit messages carry the detail; a doc is written when it explains a design, not to record a step.

### 5. Decisions (the user, 2026-10-28)
- One thing at a time; no parallel sessions.
- Master gets a step once its scenario shows it works.
- Spectators and replays are not dealt with (the user, 2026-10-28); spectators' 240 Hz blocker is kept in STATUS.md.
- Debug tools and tests are kept in scope, not skipped.
- The real TF.EX server later on (not hosting our own): the Switch speaks TF.EX's protocol unchanged, and our fork
  (docs/SERVER-DIFF-2026-10-26.md) is only a local stand-in for tests. A server change the Switch needs (#283's local players)
  goes upstream, or the Switch does without it.

### 6. Hardware per step
One console session per landed step, with a checklist generated from the log lines the step names; bugs seen there go
to the step that owns the flow, not into a general backlog.

### Lessons
1. **A unit is cheap; noticing it is missing is not.** TriggerArrow, Ice and VersusAwards each took a few lines of translate.toml,
   yet sat untranslated after v0.27 until a hand inventory found them. The hand FirstUnported list kept refusing three variants a
   week after their patches were generated. A hand list that mirrors TF.EX goes stale.
2. **Translator constructs turn up one per build, mid-feature.** This session: goto, int[,], C# 14 extension calls, a span argument
   to a rewrite, plain MessagePack arrays; v0.27.0: 8 more. Each cost a build-and-read cycle inside a feature.
3. **The measuring tools drift.** `translate.sh coverage` at fbeec67: 38 of 626 files fail on headers the coverage run doesn't
   write (tfexgen_State_Api.hpp, tfexgen_GlueFrMods.hpp, ...), so 479 methods, MatchmakingService and NetplayManager included,
   count as "doesn't compile" though the module builds them. Its headline (52% of lines) is wrong, and its ranking can't be trusted.
4. **The desyncs were ours.** The rematch window (the browser's netplay build), 240 Hz's tick rounding, wide MatchStats: each was the
   Switch's or the page's side, never TF.EX. Comparing against the PC comes first.
5. **A PASS doesn't show the new code ran.** smoke lobby 173623 passed with the three variants on, but no Ice, TriggerArrow or
   VersusAwards hook fired: a 600-tick match has none of them.
